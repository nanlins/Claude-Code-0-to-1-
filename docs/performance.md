# 性能压测报告

> 命令：`npm run bench`（全本地，无网络）

## 基准结果（Windows 10, Node 20, 2026-08）

| 操作 | 次数 | 耗时 | 单次延迟 |
|------|------|------|---------|
| 任务 create+claim+complete | ×200 | ~20.7s | ~103ms/次 |
| write_file（1KB） | ×100 | ~354ms | 3.5ms/次 |
| read_file（1KB） | ×100 | ~66ms | 0.66ms/次 |
| agent 循环 3 轮（Mock） | 1 | ~55ms | — |
| 并发 10 个文件读写 | 1 | ~43ms | — |
| 压缩管线（0 API） | ×100 | ~4ms | 0.04ms/次 |
| 权限判断 | ×1000 | ~2ms | 0.002ms/次 |
| LLM 压缩摘要（单次） | 1 | ~1ms | — |

## 分析

### 健康指标 ✅
- **压缩管线**：0.04ms/次，四层压缩几乎零开销
- **权限判断**：0.002ms/次，非常快
- **文件读写**：~3.5ms/次，正常
- **agent 循环**：55ms 跑完 3 轮（Mock），框架开销小
- **并发文件**：10 个并行仅 43ms，并发执行有效

### 需关注指标 ⚠️
- **任务系统**：~103ms/次，是唯一瓶颈

**瓶颈原因**：
1. **proper-lockfile 文件锁**：每次 claim/complete 要创建/删除锁文件（Windows 上开销大）
2. **文件 IO 次数多**：lock → read → write → unlock ≈ 4-6 次文件操作
3. 这是"文件系统即数据库"设计 + 并发安全的**必要代价**，非 bug

**优化已做**：
- JSON 输出压缩（去掉缩进），减少写入字节
- 锁参数已最小化（minTimeout 5ms）

**未做（需权衡）**：
- 去除文件锁会牺牲并发安全（多 agent 认领冲突）
- 换 Redis 存储任务可大幅提速，但失去"文件系统可调试"特性

## 结论

框架核心（循环/压缩/权限/并发）性能**优秀**。任务系统的文件锁开销是**有意的安全设计**，在真实场景（任务数少）下可忽略；若要处理数千任务，可考虑 Redis 存储任务状态。
